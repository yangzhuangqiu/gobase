# gobase 文档编写规范

本文统一各模块的文档分层、内容边界和维护规则。目标不是让每个模块拥有更多文档，而是让使用者能按最短路径找到答案，并让每条稳定语义只有一个清晰的权威位置。

## 1. 文档要解决的问题

模块文档需要依次回答三类问题：

1. 这个模块解决什么问题，是否适合当前场景？
2. 使用者应如何完成一个具体任务，并避开常见错误？
3. 模块为什么这样设计，运行时究竟如何工作？

对应的标准分层是：

```text
<module>/README.md
  -> docs/guides/<module>-usage.md
  -> docs/architecture/<module>-design.md
  -> examples/<scenario>/
```

不是每个模块都必须同时拥有全部文档。简单、稳定、没有复杂生命周期的模块可以只保留 README；只有出现足够的使用场景或设计复杂度时才增加 Guide 或 Architecture。

## 2. 三层文档职责

### 2.1 模块 README：模块入口

README 面向第一次接触模块的使用者，负责建立边界、给出最短可运行路径，并把读者导向更详细的文档。

推荐结构：

1. 设计范围与目标：`In Scope` / `Out of Scope`。
2. 核心对象与职责。
3. 最小使用示例或推荐入口。
4. 公共入口与核心契约。
5. 配置模型和关键默认值。
6. 错误语义。
7. 运行时语义：生命周期、并发、资源所有权和释放责任。
8. 最佳实践摘要，并链接到 Guide 的权威章节。
9. Open Gaps / Future Improvements。
10. File Map。
11. Guide、Architecture 和可运行示例链接。

README 应保持模块作用域，只描述本模块的职责、契约和运行语义。跨模块构建顺序、系统工作流和发布流程应放入 `docs/` 下的系统文档，不应塞入单个模块 README。

README 不承担以下职责：

1. 罗列所有长场景和完整配置组合。
2. 展开设计争论、备选方案和内部算法细节。
3. 复制 Guide 的完整最佳实践和排障内容。
4. 记录未发布版本的迁移说明或开发过程。

### 2.2 Guide：任务与最佳实践

Guide 面向已经决定使用模块的开发者，按实际任务组织内容，回答“怎么玩”和“出问题怎么办”。

Guide 默认以模块能力为边界：只展开该模块提供什么能力、如何直接使用、默认和失败语义。具体实现或上层编排属于其他模块时，只在入口选择或相关文档中提供短说明和链接，不复制对方的完整代码、配置表或排障矩阵。`app`、`app-runtime` 等职责本身就是跨模块编排的模块，可以在自身 Guide 中完整说明整合路径。

例如，Config Guide 负责配置层、优先级、读取、监听和 Provider SPI；Nacos/Consul 的 bootstrap schema、SDK 生命周期与监听算法分别属于对应 provider 模块；通过 app 使用配置的完整装配路径属于 App Guide。

Guide 的主线是“提供哪些能力 -> 如何配置或启用 -> 业务如何使用 -> 产生什么可观察结果”，不能按源码类型或公共 API 顺序组织成参考手册。

#### 2.2.1 先建立能力总览

Guide 开头先说明模块提供哪些主要能力，以及使用者如何选择入口。能力总览不是公共 API 清单；每一项能力应表达一个能够被配置、启用并用于完成业务任务的稳定能力。

推荐使用能力矩阵：

| 能力 | 解决的问题 | 配置或启用入口 | 默认状态 | 业务使用入口 | 不适用场景 |
|---|---|---|---|---|---|
| `<能力>` | `<业务问题>` | `<Option/Config/Builder>` | `<启用/关闭/fallback>` | `<Runtime/API/注入对象>` | `<明确边界>` |

能力总览至少说明：

1. 模块提供的主要能力和各自解决的问题。
2. 哪些能力默认可用、默认关闭或使用 fallback。
3. 哪些能力需要显式声明、配置或注册后才生效。
4. 配置入口与业务消费入口分别是什么。
5. 常规入口、高级入口和不适用场景如何分流。

多模块聚合 Guide 先给出模块选择表，再展开各模块能力。简单模块可以合并“能力总览”和“选择入口”，但不能让读者通读全文后才知道模块能做什么。

#### 2.2.2 配置必须说明能力如何真正生效

Guide 不只罗列配置字段，还要解释配置如何使能力进入可用状态。每项非平凡能力应说明默认值、零值语义、启用条件、依赖、声明叠加规则、覆盖优先级、生效阶段、热更新边界和失败结果。

推荐使用配置/启用契约表：

| 配置项或入口 | 默认值 | 零值语义 | 启用条件 | 覆盖或叠加规则 | 生效阶段 | 冲突或失败结果 |
|---|---|---|---|---|---|---|
| `<配置>` | `<默认>` | `<未设置含义>` | `<何时真正可用>` | `<追加/覆盖/冲突>` | `<Build/Run/Refresh>` | `<error/降级/no-op>` |

写作时区分以下信息，避免把所有输入都称为“配置”：

1. **稳定声明**：应用长期声明的 Provider、validator、watch 策略或模块能力。
2. **单次运行输入**：CLI、测试或宿主仅为本次 Build 提供的覆盖。
3. **运行期配置**：Build 后允许热更新的窄配置及其拒绝语义。
4. **业务使用参数**：一次业务调用的输入，不属于模块配置模型。

只声明入口不一定表示能力已经生效。Guide 必须明确前置资源、组合条件和生效阶段，并说明多次声明是追加、覆盖还是冲突；配置失败是 fail-fast、降级还是 no-op；关闭后该能力是否仍可读取或调用。

#### 2.2.3 业务场景必须形成使用闭环

重要业务场景按照以下顺序组织：

```text
业务目标 -> 前置条件 -> 配置/启用 -> 业务使用 -> 可观察结果 -> 失败处理 -> 资源释放 -> 验证方式
```

其中：

1. **业务目标**说明场景要完成的任务，不以方法名作为目标。
2. **前置条件**说明依赖的模块、资源和已完成阶段。
3. **配置/启用**展示让能力真正生效所需的最小声明和输入。
4. **业务使用**展示业务如何取得并消费能力，不复制完整工程。
5. **可观察结果**说明返回值、状态变化、发布版本、输出或副作用。
6. **失败处理**说明调用方如何按稳定错误语义分支，以及失败后什么状态仍然有效。
7. **资源释放**说明谁负责 Close、取消、等待和保留关闭错误。
8. **验证方式**说明如何通过测试、状态、Explain、日志、指标或可运行示例确认结果。

简单场景至少包含“配置/启用、业务使用、可观察结果”。涉及资源、并发、热更新、回滚或降级的场景，还必须说明失败处理、资源释放和验证方式。多个场景共享同一套配置契约时应链接权威章节，不在每个场景中复制完整配置表。

推荐结构：

1. 能力总览与入口选择：主要能力、常规路径、高级路径和不适用场景。
2. 最小使用闭环：配置或启用能力、业务使用和预期结果。
3. 配置/启用模型：默认值、零值、依赖、优先级、叠加规则和生效阶段。
4. 按业务目标展开的常见场景。
5. 生命周期、失败处理和资源释放。
6. 测试与验证方式。
7. 最佳实践。
8. 常见问题与排障表。
9. 可运行示例和相关文档。

最佳实践的权威入口放在 Guide。README 只保留高频摘要，Architecture 解释这些实践背后的设计原因。

Guide 中的示例必须体现生产上正确的资源和错误处理方式。例如 Build 成功后必须保证 Close，业务错误与关闭错误不能互相覆盖，timeout 不能被描述成强制终止 goroutine。

Guide 不承担以下职责：

1. 按源码文件逐项解释实现。
2. 重复完整架构推导。
3. 把所有 API 写成参考手册。
4. 用历史兼容逻辑干扰当前推荐路径。

### 2.3 Architecture：是什么、为什么、怎么做

Architecture 负责架构原则和精确运行语义。它不是功能列表、源码导读或开发历史，而是一份可审查、可验证的设计论证：从原始问题与约束推导设计决策，说明当前实现如何保证预期结果，并定义失败后仍然成立的语义。

统一使用以下推导顺序：

1. **是什么**：模块解决什么原始问题，目标、非目标和边界是什么。
2. **为什么**：为什么选择当前方案，关键设计决策、代价和备选方案是什么。
3. **怎么做**：对象模型、依赖方向、状态机、生命周期、失败路径和内部实现如何保证前述目标。

#### 2.3.1 设计决策必须形成论证

重要设计决策按照以下顺序说明：

```text
约束 -> 选择 -> 原因 -> 实现机制 -> 对外结果 -> 代价 -> 未选择方案
```

其中：

1. **约束**说明当前设计必须同时满足的真实要求，不能只写“为了扩展性”“为了健壮性”等抽象目标。
2. **选择**明确当前采用的方案，避免只罗列实现对象。
3. **原因**解释该方案为什么能够解决原始问题。
4. **实现机制**说明代码通过什么流程、状态或数据结构兑现设计，但不逐文件复述源码。
5. **对外结果**描述调用方能够观察和依赖的语义。
6. **代价**说明复杂度、性能、容量、兼容或扩展限制。
7. **未选择方案**只保留仍有长期解释价值的备选方案及拒绝原因，不记录按时间排列的历史实现。

只有影响公共语义、模块边界、依赖方向、生命周期、资源所有权、并发模型、错误语义或未来演进能力的选择，才需要上升为架构决策。局部函数拆分和普通实现细节留在代码中。

#### 2.3.2 架构图与核心流程

Architecture 使用最小必要的可视模型表达静态结构和动态行为：

1. 涉及三个及以上核心对象或模块、跨模块依赖、资源所有权或禁止的反向依赖时，提供边界/依赖图。
2. 存在三个及以上依赖阶段、资源获取、提交或回滚时，提供核心流程图。
3. 对象存在合法与非法状态转换、并发调用或不可逆终态时，提供状态图。
4. 简单的一次调用或两个对象关系优先使用文字，不为装饰而画图。

每张图后必须用正文解释：

1. 节点的责任和边界。
2. 箭头表示调用、依赖、数据流还是所有权转移。
3. 哪些资源是 owned、borrowed、shared 或 transferred。
4. 核心流程的阶段顺序、commit point、失败分支和回滚方向。
5. 状态图的触发条件、非法转换、失败状态和终态。

图必须描述当前真实实现，不能把规划中的模块、流程或保证画成现状。架构图回答“谁与谁是什么关系”，核心流程回答“一次操作如何推进”，状态图回答“对象可以处于什么状态以及如何转换”，三者不能互相替代。

核心流程推荐先给出阶段总览，再用表格解释精确语义：

| 阶段 | 输入与前置条件 | 主要动作 | 取得或转移的资源 | 失败结果 | 成功输出 |
|---|---|---|---|---|---|
| validate | 声明和运行输入 | 校验边界与冲突 | 无 | 返回声明错误 | 有效计划 |
| acquire | 有效计划、context | 获取运行资源 | 记录已取得资源 | 进入逆序回滚 | 候选对象 |
| commit | 完整候选对象 | 发布结果并转移所有权 | 交给最终所有者 | 按提交后语义处理 | 可交付对象 |

#### 2.3.3 运行时语义必须可验证

Architecture 对 Build、Refresh、Run、Shutdown、Close 等关键流程，至少说明：

1. commit point 在哪里，提交前后失败语义有何不同。
2. 失败后对象处于什么状态，旧状态是否保留，是否允许重试或重建。
3. 已取得资源由谁按什么顺序回滚，清理错误是否与原始错误聚合。
4. 资源属于 owned、borrowed、shared 还是 transferred，最终由谁关闭。
5. context 能中断实际工作还是只结束当前调用者等待；底层不响应取消时如何收敛。
6. 操作是否允许并发、重复调用，是否幂等，以及所有调用者观察什么结果。
7. error、panic、降级和通知失败分别如何传播，是否保留稳定错误码与底层 cause。

存在非平凡失败分支时，使用失败矩阵集中描述：

| 阶段 | 失败原因 | 对外错误 | 对象状态 | 回滚或清理 | 能否重试 |
|---|---|---|---|---|---|
| 声明校验 | 输入冲突 | 稳定声明错误 | 未构建 | 无资源 | 修正输入后可以 |
| 资源获取 | 下游失败 | 保留下游 cause | 未提交 | 逆序关闭已取得资源 | 取决于 cause |
| 提交后通知 | 回调失败 | 通知错误 | 新状态已提交 | 不伪装成未提交 | 后续事务可继续 |

边界不变量必须写成可观察、可测试的结果，并能映射到实现或契约测试。例如使用“至多执行一次底层 Shutdown；单个调用者 timeout 不修改共享停止结果”，而不是笼统写“Shutdown 并发安全”。

推荐内容：

1. 要解决的问题、设计目标和非目标。
2. 核心设计选择及原因。
3. 核心对象、依赖方向和数据模型。
4. 架构图、核心流程和公共契约背后的精确语义。
5. 失败路径、回滚、资源所有权和幂等语义。
6. 错误码、日志、指标和可观测性。
7. 可由测试验证的边界不变量。
8. File Map。

以下内容按模块实际复杂度增加，不要求为了目录完整而创建空章节：

1. 状态机、生命周期、并发和 context 边界。
2. 配置优先级、容量、性能或安全边界。
3. 备选方案与取舍。
4. Open Gaps / Future Improvements。

统一的是必须回答的语义问题，不是固定标题。作者可以合并或调整章节，但不能因此省略适用的设计决策、核心流程、失败语义和可验证不变量。

Architecture 必须描述当前真实实现。尚未实现但更理想的行为只能放入 Open Gaps，不能写成现有保证。内部文件结构变化时，应在同一变更中更新 File Map。

Architecture 不承担以下职责：

1. 大量复制粘贴入门代码。
2. 按任务编写操作教程。
3. 保存开发过程、会话结论或版本流水账。
4. 用抽象原则代替可验证的运行时结果。

## 3. 不默认创建独立 Contract 文档

普通模块不再单独维护 Contract 文档，避免 README、Guide、Architecture 之间出现第四份重复事实源。

契约按语义分别落位：

1. 使用者需要首先知道的公共入口、默认值和失败方式放在 README。
2. 调用步骤和场景约束放在 Guide。
3. 精确状态、优先级、不变量和实现保证放在 Architecture。
4. 接口和方法的调用契约保留在代码注释中。

只有真正跨模块或面向外部系统、需要独立版本化和逐项核对的协议，才创建专门的 Contract 文档，例如环境变量、网络协议或持久化格式契约。此类文档必须明确适用范围、权威来源和变更规则。

## 4. 内容的唯一权威位置

允许不同层级对同一主题做摘要，但不允许复制出多份同等详细的定义。

| 内容 | 权威位置 | 其他文档如何处理 |
|---|---|---|
| 模块范围、推荐入口、关键默认值 | README | Guide 展开操作；Architecture 解释原因 |
| 常见场景、最佳实践、排障 | Guide | README 摘要并链接 |
| 设计理由、状态机、不变量、精确失败语义 | Architecture | README/Guide 只写使用者必须知道的结果 |
| 公共接口的参数和返回契约 | 代码注释 | README/Guide 只引用高频入口 |
| 端到端可运行代码 | `examples/` | 文档链接示例，不复制完整工程 |
| 跨模块依赖与启动顺序 | 系统 Architecture/Workflow | 模块 README 只声明自身边界 |
| 测试和发布流程 | `docs/testing`、`docs/release` | 模块文档链接对应流程 |
| 已发布版本的用户迁移 | Release Notes 或独立 Migration Guide | 未发布阶段不编写迁移历史 |

当摘要与权威文档冲突时，不能简单选择其中一份保留；必须先对照代码和测试确定真实语义，再同步修正所有受影响位置。

## 5. 什么时候增加一份文档

### 增加 Guide

满足任一条件时考虑增加：

1. 存在三个及以上常见使用场景。
2. 常规路径和高级路径需要明确分流。
3. 配置、生命周期或失败处理容易误用。
4. 需要独立的最佳实践和排障章节。

### 增加 Architecture

满足任一条件时考虑增加：

1. 存在非平凡状态机、并发或资源所有权。
2. 默认值背后有重要取舍。
3. 模块参与跨模块依赖或启动/关闭顺序。
4. 错误、回滚、降级或兼容语义需要精确定义。

如果新增文档只是重复已有内容，应优先补充链接或重构原文，而不是增加文件。

## 6. 语义写作规则

1. **边界优先**：先说明解决什么、不解决什么，再介绍 API。
2. **语义优先**：先写 when/why 和可观察结果，再写实现细节。
3. **默认值明确**：每个可配置行为都说明默认值、覆盖方式和适用阶段。
4. **失败结果明确**：说明返回 error、panic、降级、回滚和重试条件，不使用“会处理”之类模糊表述。
5. **所有权明确**：资源由谁创建、初始化、关闭，失败时由谁回滚。
6. **阶段明确**：区分创建、Build、运行、Close，以及正常关闭和失败回滚。
7. **并发明确**：说明是否并发安全、是否幂等、context 取消能做什么和不能做什么。
8. **可观测性明确**：关键流程说明 `op/result/reason`、稳定错误码和必要指标。
9. **现状与规划分开**：当前行为写入正文，理想但未实现的能力写入 Open Gaps。
10. **示例可负责**：示例不能省略关键错误处理、Close、取消或敏感信息保护。

文档语言以中文为主，标识符、API、协议名和业内通用术语保留英文。标题和文件名保持稳定，避免因表达偏好频繁重命名。

## 7. 版本与历史信息

文档描述当前对外契约，不承担 Git 历史记录职责。

1. 模块尚未发布时，不编写 Migration Notes，不解释已删除的旧 API。
2. 已发布版本发生破坏性变化时，迁移动作进入 Release Notes；步骤较长时再建立独立 Migration Guide。
3. 设计文档可以保留仍然有解释价值的“备选方案与取舍”，但不记录按时间排列的修改过程。
4. Commit、PR 和 Issue 保存开发历史，模块文档不复制这些内容。

## 8. 变更同步规则

| 代码变化 | 必须检查和更新的文档 |
|---|---|
| 新增或修改公共入口 | 模块 README、对应 Guide、代码注释 |
| 默认值或配置优先级变化 | README 默认值、Guide 操作方式、Architecture 精确语义 |
| 生命周期、并发、所有权或失败行为变化 | README 摘要、Guide 场景与排障、Architecture、测试 |
| 错误码或日志字段变化 | README 错误语义、Architecture 可观测性、排障表 |
| 文件职责或结构变化 | README/Architecture 的 File Map |
| 跨模块编排变化 | 系统 Architecture/Workflow、相关 Guide |
| 已发布破坏性变化 | Release Notes，必要时 Migration Guide |

行为变更必须在同一变更中同步代码、测试和文档。只更新文档时，也必须对照实现和测试验证其描述的是当前行为。

## 9. 文档评审清单

提交前至少检查：

1. 读者能否在开头判断模块是否适用？
2. README、Guide、Architecture 是否各自处于正确边界？
3. 是否明确默认值、优先级、生命周期和错误结果？
4. 是否区分正常路径、失败回滚、panic 和 context 取消？
5. 示例在失败路径上是否仍能正确释放资源并保留错误？
6. 文档是否准确描述代码，而不是期望中的未来行为？
7. 最佳实践是否集中在 Guide，并由 README 链接？
8. 是否存在重复章节、过期名称或未发布迁移说明？
9. File Map、相对链接和可运行示例是否仍然有效？
10. 行为变化是否已经同步测试和相关模块文档？
11. Guide 是否完整说明主要能力、配置或启用入口、默认状态、业务使用入口和不适用边界？
12. 每项非平凡能力是否说明启用条件、优先级、叠加规则、生效阶段、热更新边界和失败结果？
13. 主要业务场景是否从配置/启用走到业务使用和可观察结果，并正确处理失败、资源释放和验证？
14. Architecture 的重要决策是否说明约束、选择、原因、对外结果和代价？
15. 复杂依赖、核心流程和状态转换是否使用了最小必要的图，并解释箭头、所有权、提交点和失败分支？
16. 关键流程是否明确失败后状态、回滚、context 和并发语义，边界不变量是否能够映射到实现或测试？
